# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Summary

QueryBoard is a multi-project AI dashboarding app: users connect a database, write a natural-language query, and an agentic LLM produces SQL + a chart spec. Frontend is Vue 3 + Vite + Pinia; backend is Express + TypeScript with PostgreSQL/Drizzle for app metadata. Auth is SuperTokens.

The frontend lives in `src/`. The backend is a separate npm package in `server/` with its own `package.json`, `node_modules`, and `tsconfig.json` — they are NOT a monorepo/workspace, so commands run inside `server/` will not see frontend deps and vice versa.

## Common commands

All from repo root unless noted. `Makefile` wraps the same npm scripts; either is fine.

```bash
# install (must run in both roots)
npm install && (cd server && npm install)

# dev (Vite on :5173, server on its own port from server/.env)
npm run dev              # frontend only
npm run dev:server       # backend only (delegates to server/)
npm run dev:all          # both via concurrently

# build / typecheck / lint / format
npm run build            # vue-tsc -b && vite build
npm run type-check       # frontend tsc + (cd server && tsc --noEmit)
npm run lint             # eslint . --max-warnings 0
npm run format           # prettier write across src/, server/src/, root

# server-only build
cd server && npm run build      # tsc → server/dist
cd server && npm run start:prod # node dist/index.js
cd server && npm run migrate    # drizzle-kit migrate
```

### Tests

Tests live under `server/src/__tests__/` (vitest) and require a real Postgres test DB — they are integration tests, not pure unit tests. Use the Makefile target which boots the docker-compose Postgres and runs `drizzle-kit push`:

```bash
make test-setup          # one-time: docker compose up postgres + create queryboard_test + push schema
make test                # vitest run
make test-watch
# Single file:
cd server && TEST_DATABASE_URL=postgresql://charting:charting_dev@localhost:5432/queryboard_test \
  npx vitest run src/__tests__/services/conversation.service.test.ts
```

### Local infra (Docker)

`docker-compose.yml` runs Postgres (container `charting-db`, db `charting`, user `charting`, password `charting_dev`) and SuperTokens core. `make docker-up` / `make docker-down` / `make docker-logs`.

### Deploy (AWS)

`make tf-plan` / `make tf-apply` from `deploy/terraform/` (region us-west-2, env `prod-west`). `make deploy-backend` builds linux/amd64 image, pushes to ECR, then `aws ecs update-service --force-new-deployment` and waits for stable. `make deploy-frontend` reads `api_domain_name` from `terraform.tfvars`, builds with `VITE_API_DOMAIN`, syncs `dist/` to S3, and invalidates CloudFront. See `DEPLOY.md`.

## Architecture

### Multi-engine factory pattern (server)

Database connections are per-project. The agent and schema explorer are decoupled from the engine via two factories — when adding a new database vendor you implement both:

- `server/src/services/query-executors/index.ts` → `createQueryExecutor(engine, config)` returns `{ execute(sql), sqlRules }`. `sqlRules` is a dialect-specific string injected into the LLM system prompt so generated SQL is correct per-engine (Athena/Presto, Postgres, MySQL, BigQuery, Redshift, Snowflake).
- `server/src/services/schema-providers/index.ts` → `createSchemaProvider(engine, config)` returns `{ detectSchema() }`.

`docs/ADDING_DATABASE_VENDORS.md` documents the contract.

### Multi-vendor LLM

`server/src/services/llm-providers/index.ts` is a factory over the Vercel AI SDK (`@ai-sdk/anthropic`, `@ai-sdk/openai`, `@ai-sdk/google`). Each project picks vendor + model. `claude.service.ts` exposes `askLLM` for one-shot calls; the agent loop is its own thing (below).

### Multi-library charts

`server/src/services/chart-libraries/index.ts` returns per-library prompt fragments (Vega-Lite/Chart.js/ECharts/Plotly). The chart spec is generated by the agent in whichever schema the project's library expects; the frontend `ChartRenderer` dispatches to the matching renderer.

### Agentic chart generation

Core file: `server/src/services/chart-agent.ts` (with `chart-agent-handlers.ts`, `chart-agent-prompts.ts`, `agent-tools.ts`). It runs a tool-use loop with 4 tools: `list_tables`, `get_columns`, `run_query`, `create_chart`. `create_chart` is terminal. Hard cap of 20 turns; on turns 19–20 with query results in scope, the prompt forces a `create_chart` call. Streams progress to the frontend via SSE events `step` / `thinking` / `result` / `error`. Refinements distinguish visual-only edits (skip DB) from data edits (re-run `run_query`). `chart-chat-agent.ts` is the conversational Q&A variant over an existing chart; `qa-agent.ts` is general project Q&A. See `docs/AGENTIC.md`.

### Server bootstrap order

`server/src/index.ts` does, in this order: load config → connect Postgres pool → run drizzle migrations from `server/migrations/` → seed projects from `server/projects.config.json` → wait for SuperTokens core → seed roles → create initial admin → load refresh schedules (`refresh-scheduler.ts`, node-cron) → mount routes. Most route groups are mounted under `/api/projects/:projectId/...` behind `verifySession()`; `/api/admin` requires the `admin` role; `/api/shared/:token` is the only unauthenticated app route (read-only public dashboards).

### App database (Drizzle)

Schema in `server/src/db/schema.ts`, SQL migrations in `server/migrations/`. Migrations are auto-applied at server start — do not call them out-of-band in dev. Use `drizzle-kit` from inside `server/` (`npm run migrate`, or `npx drizzle-kit push` for the test DB). `drizzle.config.ts` lives in `server/`.

### Frontend wiring

Vite dev server expects the backend on a separate port; `src/services/api.ts` is the shared Axios instance and reads `VITE_API_URL` / `VITE_API_DOMAIN` (set at build time for prod). State is in Pinia (`src/stores/`); routes in `src/router/`. SSE for the agent is consumed in `AIChartGenerator.vue`.

### Auth

SuperTokens (self-hosted core via docker-compose). Roles seeded at startup (`auth.ts`, `ROLES`). `middleware/roles.ts` provides `requireRole`. Project-scoped permission checks live in `services/permission.service.ts` and `middleware/dashboard-access.ts` / `middleware/conversation-access.ts`. `AUTH_SETUP.md` covers OAuth provider setup (Google/GitHub/Microsoft).

## Conventions worth knowing

- ESM throughout (`"type": "module"`). Server imports use `.js` extensions on relative paths even though sources are `.ts` — this is required for Node ESM + tsx, don't "fix" them to remove the suffix.
- `npm run lint` runs with `--max-warnings 0`; CI/local should be clean before commit.
- Don't hand-edit anything in `dist/` or `server/dist/`.
- When changing the DB schema, add a Drizzle migration under `server/migrations/` rather than relying on `drizzle-kit push` (push is only for the test DB).
- Secrets for DB credentials can come from AWS Secrets Manager — see `services/secrets.service.ts` and `docs/SECRETS_MANAGER.md`.
